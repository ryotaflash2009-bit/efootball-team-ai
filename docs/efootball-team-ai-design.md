## 第1章 エグゼクティブサマリー

**プロダクト**: eFootball Team AI — eFootball（サッカーゲーム）の選手・監督・ブースター・Tier データを集約し、検索・比較・育成・スカッド編成を行える Web サービス。最終目標は「ユーザーの目的・所持選手・コイン数・戦術を理解し、根拠付きで助言する AI サービス」。

**基本構造**:
- UI と機能の基準 = **eFHUB**
- 主要データソース = **eFHUB**
- 補完・照合データソース = **eFootball World**
- 通常の画面表示 = **自前統合データベース**（外部サイトを毎回叩かない）

**技術構成**（初版）: Next.js（App Router）+ TypeScript + Tailwind CSS + Zod + ローカル JSON 保存。将来 PostgreSQL へ移行できるよう「データ取得層」を関数で分離。モジュラーモノリス（1つのアプリの内部を機能ごとに整理して分ける構成）。

**最初の動作版のスコープ**: ホーム / サイドメニュー / プレイヤー一覧（日本語・英語検索、OVR 並べ替え）/ 簡易な選手詳細 / データソース・取得日時表示 / ローディング・空・エラー表示 / モバイル・PC 対応。eFHUB の `player-index.json` から最大100件を取得して表示。

**今回やらないこと**: 全選手同期、World 543ページ取得、RSC 本解析、Tier 全同期、監督全機能、育成計算、スカッド完全版、認証、私の選手、私のビルド、端末間同期、コミュニティ、AI 機能、本番デプロイ、Git 初期化。

## 第2章 research.txt の内容確認

research.txt に記載された要点（原文の要約。判断は加えていない）:

- 旧プロジェクトは移行せず、正式版をゼロから作る。旧版は削除しない。
- 主要データフロー: eFHUB → 取得 → 形式統一 → 自前DB。World → 不足補完 → eFHUB と照合 → 自前DB。自前DB → 画面表示・検索・比較・育成・スカッド・AI。
- eFHUB 確認済み URL: `https://efhub.com/search/player-index.json`
- レコード例: `{"i":105845711048063,"e":"Melvin Bard","j":"メルヴァン バール","o":97}`
- 短縮キー推測: `i`=選手ID / `e`=英語名 / `j`=日本語名 / `o`=OVR（複数選手で要確認）
- 他の候補リソース: `manager-index.json` / `managers.json` / `boosts.json` / `player-tier?playerId={id}` / 個別選手ページの RSC 系レスポンス
- 監督戦術適性6種: PossessionGame / QuickCounter / LongBallCounter / OutWide / LongBall / Overload
- ブースター構造候補: `{id,name,japName,magnitude,stats:{能力名:値}}`
- eFootball World: `POST https://efootball-world.com/api/proxy/v1/api/players/search`、Payload `{page,size,sortBy,sortOrder}`、totalCount 13009 / 543ページ / 24件ずつ
- World メタ: `/api/proxy/v1/api/players/{playerId}/metadata` は いいね数・閲覧数 の可能性が高い
- `config.json` は他ゲーム名を含む無関係ファイル。データソースに使わない。
- データ優先順位: 第1=eFHUB、第2=World、通常表示=自前DB。管理者の手動修正値を自動同期で上書きしない。
- MVP は player-index.json への接続 → 先頭3件確認 → 10件保存 → 問題なければ最大100件 → 一覧・検索・並べ替え・簡易詳細・データソース表示・取得日時表示・モバイル/PC 対応。

## 第7章 ユーザーストーリー

- U8: AI に「クロス中心で戦いたい」と伝えて編成案が欲しい。（P4）

- サイドメニュー: モバイルは左からスライドイン + 背景オーバーレイ。`lg` 以上は常時表示の左カラム（240px）。
- コンテンツ最大幅 1200px、中央寄せ。

### 9-3. 各画面の定義（今回実装分）

**ホーム `/`**
- 目的: サービスの入口。実装済み機能への導線。
- 表示: サービス名、キャッチ、「プレイヤーを見る」ボタン、データ状態（取得元・取得日時・件数）、ロードマップ抜粋。
- 操作: プレイヤー一覧へ移動、サイドメニュー開閉。
- 必要データ: `/api/data-status`。
- モバイル: 縦1カラム。PC: 中央寄せカード。
- ローディング: スケルトン。データなし: 「まだデータがありません」。エラー: 「状態を取得できませんでした」。
- 完成条件: 表示され、一覧へ遷移でき、データ状態が出る。

**プレイヤー一覧 `/players`**
- 目的: 選手を検索・並べ替えして探す。
- 表示: 検索バー、並べ替えセレクト、総件数、データソース + 取得日時、選手カードのグリッド。
- 操作: キーワード入力（日本語/英語、部分一致、大小無視）、並べ替え（OVR 降順/昇順/名前）、カード選択で詳細へ。
- 必要データ: `/api/players?q=&sort=`。
- モバイル: 2列グリッド、検索バー全幅。PC: 4〜6列。
- ローディング: カードスケルトン。データなし: 「条件に一致する選手がいません」。エラー: 「選手データを読み込めませんでした」＋再試行。
- 完成条件: 最大100件表示、検索・並べ替えが機能、詳細へ遷移、データ状態表示。

**選手詳細 `/players/:id`**
- 目的: 1選手の基本情報とデータ来歴の確認。
- 表示: 日本語名、英語名、OVR、選手ID、（あれば）ポジション、データソース、取得日時、「一覧へ戻る」。今回未実装の項目（能力値/育成/比較/Tier）は「今後のバージョンで実装予定」と明記。
- 必要データ: `/api/players/:id`。
- 該当なし: `not-found`（「選手が見つかりません」）。
- 完成条件: 一覧から遷移して表示、存在しない ID で not-found。

## 第12章 eFHUB データ取得設計

### 12-1. 取得層の分離

```
UI（画面） → 内部API（/api/*） → データアクセス層（src/lib/players.ts）
                                     ├─ 現在: ローカル JSON 読み込み
                                     └─ 将来: PostgreSQL / Prisma へ差し替え
外部取得（scripts/*.mjs） → 生データ保存（src/data/*.json） → （将来）正規化 → DB
```

- 画面・内部 API は「外部サイトを直接叩かない」。必ず自前データを参照。
- 外部取得はバッチ（`scripts/` 以下のスクリプト）でのみ実行。

### 12-2. 取得スクリプトの要件（`fetch-player-index.mjs`）

- URL: `https://efhub.com/search/player-index.json`（GET）
- タイムアウト 20 秒（`AbortController` 使用）
- User-Agent を明示（`eFootball-Team-AI-dev/0.1`）
- 成功時: `Content-Type` と JSON パースを確認 → 配列であることを検証 → 先頭最大100件を抽出
  - 各要素を `{ i, e, j, o }` の形か検証（Zod）。ID は精度保持のため**文字列化**して保存。
- 保存:
  - `src/data/players.sample.json`: `{ players: [...], _meta: {...} }`
  - `src/data/meta.json`: `{ source, sourceUrl, method, fetchedAt(ISO8601), totalReceived, savedCount, note }`
- 失敗時（ネットワーク / 非200 / 非JSON / 非配列 / 検証失敗）: **ファイルを書かず、非0で終了**。再取得しない。

### 12-3. 将来の全件取得（初版では行わない）

- レート制御: リクエスト間隔 ≥ 1s、同時実行 1、指数バックオフ、429/5xx 対応、途中再開、冪等（同じ処理を再実行しても重複しない）。
- 取得件数・ファイルサイズの異常検知（前回比 ±50% で警告・停止）。

## 第13章 World データ取得設計（将来）

- `POST https://efootball-world.com/api/proxy/v1/api/players/search`、`{page,size,sortBy:"CREATED_AT",sortOrder:"DESC"}`。

## 第14章 RSC 解析方針

- RSC（React Server Components）= Next.js がページ描画に使うストリーム形式。安定した公開 API ではなく、サイト更新で形が変わりやすい。
- 方針:
  1. まず静的 JSON / 通常の JSON API を探す（優先）。
  2. RSC しかない場合、`self.__next_f.push([...])` のペイロードを収集し、JSON 断片を連結してパース。
  3. パーサは**バージョン管理**（`parser_version`）し、想定外構造を検知したら停止・通知。
  4. RSC 由来データは信頼度を1段下げ、可能なら World と照合。
- 初版では RSC 解析を行わない（選手詳細は `player-index.json` の範囲のみ）。

## 第15章 ID 照合とデータ正規化

- eFHUB ID と World ID が同一と仮定しない。
- 内部 ID 体系:
  - `internal_player_id`（自前の主キー、UUID または連番）
  - `efhub_player_id`（文字列）
  - `world_player_id`（文字列、後で付与）
  - `game_card_id`（ゲーム内カード識別、判明したら）
- 「実在選手」と「ゲーム内カード」を分離:
  - `players`（実在選手: 名前・国籍・生年など）
  - `player_cards`（カード: OVR・カード種別・能力値・リリース）
- 自動照合の条件（すべて一致で自動マージ候補）: 正規化英語名 + カード種別 + OVR + リリース時期。
- 人手確認が必要な条件: 名前の表記揺れ、OVR 1差、カード種別不明。
- 初版: `player-index.json` の4項目のみ扱うため、`efhub_player_id` = `i`、名前 = `e`/`j`、OVR = `o` をそのまま保持。照合は将来。
