# ロールバック計画(Vercel接続時、2026-09-14)

調査日: 2026-09-14。本書は計画のみ。`ci-cd-and-auto-update.md`7章の既存方針を、Vercel接続を具体的に想定して補足する。

---

## 1. サイト本体(コード)のロールバック

- Vercelは過去の各デプロイを保持し、ダッシュボードから**ワンクリックで以前のデプロイへ切り戻せる**(標準機能、追加実装不要)。
- 切り戻しは、コードの`git revert`を伴わない「配信先の切り替え」であるため即座に反映される。ただし、**根本原因の修正(コード側の`git revert`やhotfix)は別途mainへ反映する必要がある**(切り戻しは応急措置)。
- 失敗デプロイ(ビルドエラー等)は、Vercelが自動的に「Failed」として扱い、直前の正常なProduction Deploymentは変更されない(=失敗デプロイが自動的に本番へ昇格することはない)。

## 2. 参照データ(SQLite/将来の代替方式)のロールバック

- `reference-data-update.md`5章の既存方針(日付・ハッシュ付きファイル名での版管理、直近数世代の保持)をそのまま踏襲する。
- 現状はサイト本体のデプロイと参照データが結合している(`sqlite-production-compatibility-audit.md`で指摘済み)ため、参照データだけのロールバックは「直前のコードデプロイへの切り戻し」と実質的に同じ操作になる。将来B/E方式(Supabase移行・オブジェクトストレージ化)へ移行すれば、参照データだけを独立してロールバックできるようになる。

## 3. Supabase(認証・ユーザーDB)のロールバック

- DBマイグレーションは、`ci-cd-and-auto-update.md`7章の既存方針どおり、**マイグレーションごとに逆マイグレーションSQLを人が用意する運用**とする(自動生成された逆マイグレーションを無条件に信頼しない)。
- 現状(本フェーズ時点)ではユーザーDBの本番マイグレーション自体が未実施であり、ロールバック対象は存在しない。

## 4. 環境変数のロールバック

- Vercelの環境変数はデプロイ単位でスナップショットされないため、環境変数の変更ミスは**手動で元の値へ戻す**必要がある。変更前に現在の設定値を記録しておく運用を推奨する(実際の値をClaude Codeへは渡さない)。

## 5. Supabase URL Configurationのロールバック

- `preview-production-environment-design.md`3章の設定変更(Redirect URLsの追加)は、Supabaseダッシュボード上で**追加した項目を削除するだけ**で元に戻せる。localhostの既存設定は今回変更しないため、ロールバック対象にならない。

## 6. 今回の監査自体のロールバック

- 本フェーズで作成したのは`docs/production-readiness/`配下の監査文書のみであり、アプリ本体・設定ファイルは変更していない。コミット前であれば、ブランチ`chore/vercel-readiness-audit`ごと破棄すれば元に戻せる(**ただし今回はコミット・pushの指示がないため、実際の破棄操作もタスク要求外**)。
