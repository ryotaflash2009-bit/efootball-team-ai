# クラウドユーザーDB候補比較

調査日: 2026-09-11。料金は各社公式サイト・第三者解説記事(2026年時点)に基づく。**契約直前に必ず公式サイトで再確認すること。**

## 1. 保存対象データ(将来のユーザーDB)

`architecture-audit.md`の分類Aに基づき、ユーザーDBが保存すべきデータは: Favorites、My Team、保存ビルド(`buildIntent`込み)、保存スカッド、スカッドテンプレート。加えて将来機能として: 診断履歴、プロフィール、フレンド関係、契約状態(`subscription_state`、設計のみ)。

**参照データ(選手・監督・ブースター等13,009件超のWorldカードデータ)はユーザーDBとは別物であり、統合しない**(理由は「推奨構成」で詳述)。

## 2. 候補比較

比較対象: **Supabase PostgreSQL**、**Firebase Firestore**、**Neon PostgreSQL**、**Vercel経由のPostgres(現在はNeon統合)**。

> 重要な前提確認(2026年時点): **「Vercel Postgres」は単独サービスとして新規に持てなくなっている。** 既存のVercel PostgresデータベースはすべてNeonへ2024年12月に自動移行済みで、新規プロジェクトはVercel Marketplace経由でNeonを選ぶ形になっている(Vercel公式ドキュメント・Neon公式移行ガイドで確認)。つまり「Vercel Postgres」と「Neon」は事実上統合されており、比較表では両者をまとめて扱う。

| 項目 | Supabase PostgreSQL | Firebase Firestore | Neon PostgreSQL(Vercel Marketplace経由含む) |
|---|---|---|---|
| データモデル | リレーショナル(標準SQL) | ドキュメント指向NoSQL | リレーショナル(標準SQL、Postgres本体) |
| ユーザー別データ分離 | RLSで実現(行単位) | セキュリティルールで実現(ドキュメント単位) | RLSは**Postgres標準機能としては利用可能だが、認証機構が別サービスになるため「認証済みユーザーのIDをどうRLSへ渡すか」を自前で設計する必要がある** |
| 行レベルセキュリティ | ✅ ネイティブ対応、Supabase Authと直結 | セキュリティルール(RLSと同等の目的だが構文・思想が異なる) | ✅ Postgres標準のRLSは使えるが、認証との統合は自前実装 |
| トランザクション | ✅ 標準SQLトランザクション | 限定的(バッチ書き込み・トランザクションはあるが操作数に制限) | ✅ 標準SQLトランザクション |
| JSONデータの扱い | `jsonb`型で柔軟に格納可(育成配分・`buildIntent`のような構造化データに向く) | ネイティブでドキュメント=JSON的構造(親和性は高いが正規化がしにくい) | `jsonb`型で同様に格納可能 |
| 関連データ(外部キー) | ✅ 標準的な外部キー制約 | サブコレクション・参照フィールドで疑似的に表現(制約はアプリ側で担保) | ✅ 標準的な外部キー制約 |
| バックアップ/復元 | 自動バックアップ(Pro以降)、Point-in-Time Recovery(PITR)は上位プランで対応 | Google Cloud側のエクスポート/インポート機能 | ブランチ機能を使った「時間指定でのブランチ作成」がPITR相当として利用可能(詳細は上位プランで拡充) |
| 無料枠 | 500 MBデータベース、1 GBファイルストレージ、2プロジェクトまで(2026年時点) | 1 GiBストレージ、日次読み書き上限あり | 0.5 GBストレージ、100 CU-時間/月、最大100プロジェクト(2026年時点) |
| 月額費用(超過時) | Proプラン $25/月〜 | 従量課金(Blazeプラン。読み取り$0.06/10万件〜) | Launchプラン $0.106/CU時間〜、Scaleプラン $0.222/CU時間〜(ストレージは別課金、2025年に$1.75→$0.35/GB月へ値下げ) |
| 接続数 | Postgres標準の接続プーリング(Supavisor)あり | 該当なし(NoSQLのため接続数の概念が異なる) | サーバーレスドライバがコネクションプーリングを内蔵 |
| スケーリング | 垂直スケール中心(プラン変更) | 自動スケール(NoSQL特性上、水平スケールしやすい) | **オートスケール+アイドル時にゼロへスケールダウン**(コスト効率が良い) |
| 将来のReact Native対応 | 対応良好(前章参照) | 対応良好だが設定がやや複雑 | Postgresへの直接接続はモバイルからは非推奨(必ずNext.js API経由にする設計が前提になる。むしろこれは望ましい制約) |
| データ移行(localStorage→クラウド) | 標準SQLの`INSERT`で単純 | ドキュメント形式への変換が必要(構造をNoSQL向けに再設計) | 標準SQLの`INSERT`で単純 |
| ベンダーロックイン | 中(Postgres標準なので他のPostgresホスティングへ移せるが、Auth/RLSの一部はSupabase固有) | 高(Firestore特有のクエリ・データモデルからの脱却コストが大きい) | **低い(素のPostgresであり、他のPostgresホスティングへの移行が最も容易)** |
| 管理画面 | Supabase Studio(テーブルエディタ・SQL実行・ログを統合) | Firebaseコンソール | Neonコンソール(Drizzle Studio統合のテーブルエディタ、SQLクライアント) |
| 監査ログ | 上位プランで拡充 | Google Cloud監査ログとの連携 | 上位プランで拡充 |
| 障害対応 | Supabase運営に依存 | Google Cloudの高い可用性実績 | Neon運営に依存(Vercel経由でも実体はNeon) |
| 個人開発での運用負担 | **中(SQLの知識は要るが、認証と一体運用できる分だけ管理対象が少ない)** | 中〜高(NoSQL設計の学習コスト、Google Cloud特有の概念) | 中(SQLの知識は要るが、ブランチ機能により「ステージング用DBを一瞬で複製」できる利点が大きい) |

## 3. 参照データ(SQLite)を今すぐユーザーDBへ統合すべきか

**結論: 統合すべきではない(現時点)。**

理由:
1. 参照データ(選手・監督・ブースター等)は**全ユーザー共通の読み取り専用データ**であり、ユーザーごとの行レベルセキュリティが不要。ユーザーDBのRLS運用にとってノイズになる。
2. 参照データは13,009件超と件数が大きいが更新頻度は低い(半自動更新、`reference-data-update.md`参照)。ユーザーDB(高頻度な読み書き)と混在させると、参照データの更新作業がユーザーの読み書きへ影響するリスクがある。
3. 現行のSQLite読み取り専用アクセスは**変更コストが低く、動いている**。無理に移行する技術的必然性が今はない。
4. 将来的には「参照データもクラウドDBへ移す」選択肢自体は排除しないが、それは**ユーザーDB導入とは独立した意思決定**として扱うべき(本設計書では役割分離を推奨するに留め、参照データの移行是非は別途判断する)。

## 4. 所見

- Supabase PostgreSQLは、認証(Supabase Auth)とDB(Postgres+RLS)が同一基盤で完結するため、個人開発者にとって管理対象を最小化できる。
- Neon単体は「素のPostgres」としての柔軟性・低ロックインが魅力だが、認証を別サービス(Clerk等)と組み合わせる前提になり、RLSとの統合を自前で設計する必要が生じる。
- Firebase Firestoreは、本プロジェクトの「リレーショナルなユーザーデータ(My Team→保存ビルド→保存スカッドという明確な親子関係)」との相性が他の2候補より劣ると判断する。
