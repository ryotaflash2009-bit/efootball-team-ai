# 参照データ Supabase既定化 前提条件・切戻しランブック

**本書は既定化そのものの承認ではない。** `WORLD_DATA_SOURCE`の既定値を`"supabase"`へ変更する判断(`docs/production-readiness/app-hybrid-switch-implementation-plan.md`が定義する正式な「Phase E: 既定値の切り替え」)を安全に行うための、事前チェックリストと障害時の切戻し手順をまとめたものである。

このランブック自体の追加は、Reference Data Operational Hardening(既定化前の運用強化、フェーズ番号なし)の一部であり、Phase Eそのものではない。

## 0. 目的

`WORLD_DATA_SOURCE`を`sqlite`から`supabase`へ切り替える前に、運用上必要な確認事項と、切り替え後に問題が起きた場合の最小の切戻し手順を、事前に整理しておく。

## 1. 前提条件(このランブックが対象とする範囲)

- Phase D(SQLite/Supabaseシャドー比較)が完了し、差分0件であること(完了済み、PR #13でmainへマージ済み)
- Reference Data Operational Hardening(本ランブックを含む一連の運用強化作業)が完了していること

## 3. WORLD_DATA_SOURCE設定手順(一般原則、実プロジェクト固有値は書かない)

- `WORLD_DATA_SOURCE`は文字列`"sqlite"`または`"supabase"`のみを受け付ける(それ以外は起動時エラー)。大文字小文字は区別され、前後の空白はtrimされる。
- 値の設定先は、使用しているホスティング環境の環境変数設定機能を使う(具体的な設定画面・コマンドは使用サービスに依存するため、本書では特定サービスの操作手順を書かない)。
- **秘密値(Supabase URL・鍵・接続文字列・トークン等)は、このランブックを含むいかなるドキュメントにも実際の値を書かないこと。** 例を示す場合もプレースホルダー(例: `<YOUR_PROJECT_REF>`)を使う。
- 設定変更後、実際に反映されたかどうかは、環境固有の確認手順に従うこと(本書では断定しない)。

## 4. 既定化後の検証(切り替え直後に実施)

1. `WORLD_DATA_SOURCE=supabase`環境下での全Unit Test実行
2. `npx tsc --noEmit`
3. `npm run build`
4. Phase Dシャドー比較の再実行(差分0件を再確認)
5. 主要画面(一覧・検索・フィルター・全ソート・詳細・ページング)の1280px/390px確認
6. 正常系・異常系(404・0件・意図的なSupabase遮断時の挙動)の確認
7. `sourceMeta`の値確認
8. サーバーサイドログ(`reference_data_query_failed`イベント)が想定どおり出力されること、秘密情報が含まれていないことの確認
9. Supabase書き込みが0件のままであることの確認

## 5. 障害判定(切り戻すべきかどうかの目安)

以下のいずれかに該当する場合、切戻しを検討する。

- 一覧・検索・詳細等の主要機能が継続的にエラーを返す
- サーバーサイドログで`errorCategory: server_error`または`rate_limited`が継続的に記録される
- Phase Dシャドー比較で新たな差分が検出される
- facetsが更新されず、明らかに古いまま5分(TTL)以上経過しても変わらない

## 6. SQLiteへ戻す切戻し判断・最小手順

- **通常の切戻しでは、DB rollback SQLの実行は不要。** `WORLD_DATA_SOURCE`を`sqlite`へ戻す(または未設定に戻す)だけで、コード変更なしに即座にSQLite経路へ復帰する。
- 追加したSupabase側カラム(`name_sort_key`・`efhub_name_en`・detail-extension列)は残したままでよい。SQLite側には一切影響しない。
- **rollback SQLを使う条件**: Supabase側のスキーマ自体を完全に撤去したい場合のみ(通常の障害対応では想定しない)。実行する場合は別途、対象SQL・実行者・承認者を明記した個別の作業として扱う。
- **キャッシュ再構築**: facetsのプロセス内キャッシュ(TTL 300秒)は、`WORLD_DATA_SOURCE`を`sqlite`へ戻せばSQLite側の同名キャッシュに切り替わる(Supabase側のキャッシュは単に参照されなくなるだけで、明示的な破棄操作は不要)。
- **再デプロイ要否**: 使用しているホスティング環境ごとに異なるため、**要外部確認**(本書では断定しない)。
- **dev/server再起動要否**: ローカル開発環境では、環境変数変更後にdevサーバーの再起動が必要な場合がある(Next.jsの環境変数読み込みタイミングによる)。本番環境の要否は上記と同様に要外部確認。
- **公開環境の操作権限**: ホスティング環境の環境変数を変更できる権限を持つ人(リポジトリオーナーまたはインフラ担当)が必要。

## 8. 失敗時の停止条件

- 事前チェックリスト(2章)のいずれかが未確認のまま既定化を実施しようとしている場合、作業を停止する。
- 既定化後の検証(4章)のいずれかが失敗した場合、直ちに5章の障害判定へ進み、必要なら6章の切戻しを実施する。
- 切戻し後も問題が解消しない場合(SQLite経路自体に問題がある場合)、これは今回のSupabase関連の切戻し手順の対象外であり、別途原因調査が必要。
