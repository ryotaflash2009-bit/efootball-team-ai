# 意思決定記録: 推奨構成

調査日: 2026-09-11。本書は`architecture-audit.md`・`authentication-options.md`・`database-options.md`・`hosting-options.md`の調査結果を踏まえた、現時点の第一推奨構成と代替構成をまとめる。**今回はいずれも未契約・未実装。実際の採否は上杉さんが最終決定する。**

## 1. 第一推奨構成

| 要素 | 推奨 | 理由(要約) |
|---|---|---|
| 認証 | **Supabase Auth** | DBと同一基盤(Postgres)で完結し、RLSと直結する。個人開発での管理対象を最小化できる。 |
| 本番ユーザーDB | **Supabase PostgreSQL** | 認証と同一プロジェクトで完結。RLSがユーザー別データ分離の要件と直接噛み合う。 |
| 参照データDB | **現状のSQLite(読み取り専用)を当面維持** | 全ユーザー共通の読み取り専用データであり、ユーザーDBのRLS運用と混在させる必然性がない(`database-options.md`第3章)。 |
| Next.jsホスティング | **Vercel** | Next.js公式開発元であり、App Router・APIルートの互換性リスクが最も低い。個人開発の運用負担も最小。 |
| 画像処理 | **既存の自前プロキシAPIルートを維持**(`/api/player-image/*`, `/api/world/player-image/*`) | 既に許可ホスト限定・プレースホルダーフォールバック等の安全設計が完成している。作り直す必要がない。 |
| バックアップ | **Supabaseの自動バックアップ(Proプラン以降)+ 定期的な手動エクスポート** | `backup-and-recovery.md`で詳述。 |
| エラー監視 | **Sentry(無料枠)** | 個人開発者向けの無料枠(5,000イベント/月、1ユーザー)が実用的。`monitoring-and-logging.md`で詳述。 |
| ログ | **Vercelの標準Functionログ + Sentry** | 追加のログ基盤を今は導入しない(過剰投資を避ける)。 |
| ステージング環境 | **Vercelのプレビューデプロイ機能を「ステージング」として活用** | 個人開発では専用のステージング環境を別途契約するよりも、Vercel標準のプルリクエスト単位プレビューを使う方が運用負担が小さい。 |
| 本番環境 | **Vercel本番デプロイ(Production Deployment)** | - |
| 自動デプロイ | **開発ブランチ→自動テスト→ステージング自動デプロイまでは自動化。本番反映は人の承認を必須とする**(`ci-cd-and-auto-update.md`) | 未検証コードの本番直行を避ける(タスクの明示的な要求)。 |
| ロールバック | **Vercelの過去デプロイへのワンクリック切り戻し + Supabaseのマイグレーション巻き戻し手順を別途整備** | - |
| 秘密情報管理 | **Vercelの環境変数機能(開発/プレビュー/本番で値を分離)** | 新たな秘密情報管理サービスを追加契約しない。 |

### 参照データを今すぐユーザーDBへ統合する必要はない

`database-options.md`第3章の理由により、**統合しないことを推奨**。参照データ(選手・監督データ)とユーザーデータ(アカウントごとの保存内容)は役割が根本的に異なり(全員共通の読み取り専用 vs 個人ごとの読み書き)、混在させるとRLS設計・更新運用の両方が複雑化する。

## 2. 代替構成

| 要素 | 代替 | 採用条件 |
|---|---|---|
| 認証+DB | **Clerk(認証) + Neon(DB)** | 「認証UIの作り込みを最小限にしたい」「Postgresをベンダーロックインなく持ちたい」を最優先する場合。2サービス運用にはなるが、どちらも個別のロックインが低い。 |
| ホスティング | **Cloudflare(Pages+Workers)** | 将来的に`node:sqlite`依存をなくし(参照データをCloudflare D1等へ移行する等)、エッジでの低遅延配信を最優先したい場合。ただし本タスクの調査時点では、現行のSQLite実装との相性リスクが高いため第一推奨にしない。 |

## 3. 推奨理由(まとめ)

1. **既存コードへの影響が最小**: Next.js公式ホスティング(Vercel)を選ぶことで、App Router特有の機能をそのまま使い続けられる。
2. **管理対象サービス数を最小化**: 認証とDBを同一ベンダー(Supabase)にまとめることで、個人開発者が管理すべき契約・秘密情報・障害ドメインの数を減らせる。
3. **参照データと ユーザーデータの責務分離**: 既に安定して動いているSQLite読み取り専用構成を壊さず、ユーザーデータだけを新設のクラウドDBへ切り出す設計は、変更範囲を局所化できる。
4. **段階的な移行が可能**: Supabase・Vercelはいずれも無料枠から始められ、身内テスト→招待制ベータ→一般ベータの各段階で必要に応じてプラン変更するだけで済む(サービス自体の乗り換えが不要)。

## 4. 将来のReact Native(iPhoneアプリ化)対応

- Supabase Auth・Supabase PostgreSQLはいずれもReact Native(Expo管理ワークフロー含む)からの利用実績が豊富で、`@supabase/supabase-js`をそのまま使える(`authentication-options.md`第3章)。
- Next.jsのAPIルートを「クライアントに依存しない共通バックエンド」として設計しておけば、将来のReact NativeアプリもWebと同じAPIルートを呼び出せる(データモデル・認可ロジックの二重実装を避けられる)。
- ただし、Postgresへの直接接続をモバイルアプリから行うことは推奨しない(接続情報の露出リスク)。**モバイルアプリも必ずNext.jsのAPIルート経由でデータへアクセスする設計**を今から前提にしておくことを推奨する。
