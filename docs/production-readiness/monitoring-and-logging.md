# エラー監視とログ設計

調査日: 2026-09-11。本書は設計のみ。今回は監視サービスと契約しない。

## 1. 将来必要な監視項目

| 項目 | 監視方法(想定) |
|---|---|
| サイト稼働確認 | Vercelの標準ステータス監視 + 簡易な外形監視(無料枠のUptime監視サービスを将来検討) |
| HTTPエラー(4xx/5xx) | Vercel Functionログ + Sentryのエラー集約 |
| APIエラー | 同上(APIルート内でのcatchブロックからSentryへ送出) |
| ログイン失敗 | 認証サービス(Supabase Auth等)標準のログ・アラート機能 |
| DBエラー | Supabaseダッシュボードのログ + アプリ側でのエラーハンドリング経由でSentryへ送出 |
| デプロイ失敗 | Vercelの標準デプロイ通知(メール等) |
| 画像プロキシ失敗 | 既存の`X-Image-Reason`ヘッダー等を活用し、失敗率が閾値を超えたらSentryへ通知するロジックを追加検討 |
| データ同期失敗(将来のクラウド移行機能) | `data_migrations`テーブルの失敗件数を定期的に集計し、異常値であればアラート |
| JavaScript例外 | Sentryのブラウザー側SDK(クライアントエラー捕捉) |
| Core Web Vitals | Vercel Analytics(有料)またはSentryのパフォーマンス機能(将来検討、初期版では必須にしない) |
| バックアップ失敗 | Supabase側の通知機能(契約後に確認) |
| 不正アクセス試行 | 認証サービス標準のログイン試行制限・異常検知機能 |
| レート制限 | 既存の`/api/build-intent/extract`のようなプロセス内スロットリングのログを拡張、または認証サービス標準機能に依存 |
| 利用料金増加 | 各サービス(Vercel/Supabase等)の使用量アラート機能(上限設定、`cost-estimate.md`参照) |

## 2. ログに含めてはいけない情報(タスク要求通り)

- 個人情報(氏名・住所・電話番号等)
- メールアドレス
- 保存ビルドの内容(育成配分・`buildIntent`等、ユーザーの作成物)
- 認証トークン・セッションID・パスワード(平文・ハッシュ問わず)

**設計方針**: エラーログには「どのAPIルートで」「どんな種類のエラーコードが」発生したかだけを記録し、リクエストボディ・レスポンスボディ全体をそのままログへ流さない。既存の`/api/build-intent/extract`が既に採用している「自由文全文をログへ出力しない」という方針を、将来の全APIルートに一貫して適用する。

## 3. 監視サービス候補と無料枠(今回は契約しない)

| サービス | 無料枠 | 用途 |
|---|---|---|
| **Sentry** | Developerプラン: 5,000イベント/月、1ユーザー、30日間保持(2026年時点) | エラー監視・パフォーマンス監視の第一候補 |
| Vercel標準ログ | Hobby/Proプランに含まれる範囲のFunctionログ | 追加契約不要の基礎的な可視化 |
| Supabaseダッシュボード | 無料プランにも基本的なログ・メトリクス画面が含まれる | DB側の状態確認 |

**所見**: 個人開発の初期段階では、追加の月額費用が発生しないVercel標準ログ+Supabaseダッシュボードの組み合わせで開始し、実際にエラーが増えてきた段階でSentryの無料枠を追加する、という段階的導入が現実的。
