# サイト本体の自動アップデートとCI/CD設計

調査日: 2026-09-11。本書は設計のみ。GitHub Actions等は今回設定しない。

## 1. 前提: 現状Gitリポジトリが存在しない

`architecture-audit.md`で確認した通り、正本ワークスペースには`.git`が存在しない。CI/CDを組む前に**まずGitリポジトリの初期化**が必要(`implementation-roadmap.md`の第1段階)。

## 2. 環境の分離

| 環境 | 用途 | ブランチ(想定) |
|---|---|---|
| 開発環境 | Claude Codeによる実装・ローカルの`next dev`での確認 | `develop`(または機能ブランチ) |
| ステージング環境 | 本番反映前の最終確認。Vercelのプレビューデプロイ機能を活用 | `develop`または各プルリクエスト |
| 本番環境 | 実際に利用者がアクセスする環境 | `main` |

## 3. 求められる流れ(タスク要求そのまま・実装順に整理)

```
1. Claude Codeで実装(機能ブランチ)
2. 開発ブランチ(develop)へ反映(プルリクエスト/マージ)
   ここまでは今回と同じ「正本ワークスペースでの直接作業」でも成立する
3. Unit Test          ← 自動化対象
4. audit(ja-labels, i18n-keys) ← 自動化対象
5. typecheck          ← 自動化対象
6. lint               ← 自動化対象
7. Production Build   ← 自動化対象
8. 累積ブラックボックス ← 自動化対象(可能な範囲。下記4章で詳述)
9. ステージングへデプロイ ← 自動化対象(Vercelプレビューデプロイ)
10. ステージングでヘルスチェック ← 自動化対象
11. 本番反映の承認     ← ★人の承認(自動化しない)
12. 本番デプロイ       ← 承認後に自動実行してよい
13. 本番ヘルスチェック  ← 自動化対象
14. 問題時に直前の正常版へロールバック ← 自動化対象(Vercelの標準ロールバック機能)
```

## 4. 自動化するものと、人の承認を残すものの区分(タスク要求通り)

### 自動化してよいもの

- Unit Test(既存の`npm run test`)
- audit(`npm run audit:ja-labels`, `npm run audit:i18n-keys`)
- typecheck(`npm run typecheck`)
- lint(`npm run lint`)
- Production Build(`npm run build`)
- 静的セキュリティ確認(依存関係の既知脆弱性スキャン。`npm audit`相当。GitHub Dependabot等の無料機能で対応可能)
- 可能なブラックボックス(下記「5. ブラックボックスの自動化範囲」で詳述)
- ステージングデプロイ
- ヘルスチェック(ステージング・本番とも、主要ルートのHTTP 200確認・簡易な機能スモーク)

### 人の承認を必ず残すもの(タスク要求通り、自動化しない)

- **本番公開**(ステージングでの確認結果を人が見てから、明示的に「本番へ反映する」操作をする)
- **DBマイグレーション**(スキーマ変更は必ず人が内容を確認してから実行。自動マイグレーション実行は行わない)
- **利用規約変更**
- **プライバシーポリシー変更**
- **権利表記変更**
- **課金変更**
- **重大なデータ更新**(選手データの本番反映等。`reference-data-update.md`で別途詳述)

## 5. ブラックボックスの自動化範囲(現実的な評価)

- 既存の935件のブラックボックススクリプトは、いずれも**隔離ヘッドレスChrome + Production Build上のローカルサーバー**を前提にしている(`scripts/lib/headless-chrome.mjs`がOS上のChrome/Edge実行ファイルを直接起動する設計)。
- CI環境(GitHub Actions等)でこれを動かす場合、**ランナー上にChrome/Edgeが実際にインストールされている必要がある**(GitHub Actions標準のUbuntuランナーにはChromiumが標準搭載されていることが多いが、実行可否は導入時に個別検証が必要)。
- 現実的な提案: **CI上ではUnit Test・audit・typecheck・lint・Production Buildまでを必須ゲートとし、ブラックボックス全935件は「ステージングデプロイ後に人が(または将来的にCI上で)実行する」という2段構えにする**。すべてを毎回のプッシュで自動実行すると、実行時間(実測: 935件で数十分規模)がCIのタイムアウトや無料枠(GitHub Actions無料枠は2,000分/月、`cost-estimate.md`参照)を圧迫するリスクがあるため。
- 段階的な理想形: 主要な回帰(既存機能のスモーク相当)だけを毎回自動実行し、フル935件は「本番反映前の最終ゲート」として人が明示的にトリガーする、という運用が個人開発には現実的。

## 6. 本番承認ゲートの設計

- ステージング環境のURLと、そこまでの自動チェック結果(テスト件数・PASS数)をまとめた**サマリー**を、本番反映の判断材料として提示する仕組みを想定する(具体的な通知手段は未定、実装時に検討)。
- 承認は**上杉さん本人が明示的に操作した場合のみ**進む設計とする(Vercelの本番デプロイ承認機能、またはプルリクエストの`main`へのマージ自体を承認行為とする、のいずれかを実装時に選ぶ)。

## 7. ロールバック設計

- **サイト本体**: Vercelの標準機能である「過去のデプロイへのワンクリック切り戻し」をそのまま使う(追加実装不要)。
- **DBマイグレーション**: ロールバック用のSQL(逆マイグレーション)を、マイグレーションごとに必ず用意する運用ルールとする(自動生成は保証されないため、人が確認する)。
- **参照データ(選手データ)**: `reference-data-update.md`で詳述する版管理方式で対応。

## 8. 静的セキュリティ確認

- 新規の有料サービス契約を避けるため、初期版は**GitHub Dependabot(無料)による依存関係の既知脆弱性アラート**を軸とする。
- `npm audit`をCIのステップに含める(追加ツールの導入は不要、npm標準機能)。

## 9. 未検証コードを本番へ直接自動デプロイしない、という原則の担保

- CI上で3〜10のステップがすべて成功しない限り、ステージングデプロイより先のステップ(本番反映の承認画面提示)へ進めない設計にする(いずれかが失敗したらパイプラインをそこで停止)。
- 本番デプロイのトリガーそのものを「人の承認操作」に紐づけることで、技術的にも「自動で本番へ進む経路が存在しない」状態を作る。

## 10. 未確定事項

- 具体的なCI基盤(GitHub Actions想定だが、Gitホスティング自体が未確定な現状では最終決定していない)。
- ステージング環境でのヘルスチェックの具体的な項目(主要ルートのHTTP 200確認に加えて、どこまでの機能スモークを含めるか)は実装時に確定する。
