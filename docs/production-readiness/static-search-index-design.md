# 静的検索索引の設計(2026-09-14)

対象: `player_index_entries`(47,479件、選手名・基本情報のみを持つ軽量索引)。
`reference-data-hybrid-migration-design.md`2章で決定した「索引はサーバー内静的アセットとして保持し、APIルートがメモリ内で検索・返却する」方針を、本書で実装レベルまで具体化する。

**本書の作業範囲はローカル設計・実装のみ。実Supabase・実Vercelへの接続やデプロイは行っていない。生成した索引JSONはGitへは追加しない(4章)。**

---

## 1. 方式比較

| 方式 | 概要 | 初回読込量(クライアント) | 実装コスト | 採否 |
|---|---|---|---|---|
| A. 単一JSON全件配信 | 47,479件を1ファイルにまとめクライアントへ配信 | 生3.51 MiB/gzip 1.03 MiB(PoC実測) | 低 | **不採用**(モバイル回線での初回コスト・「クライアントへの全量流出」を避ける既存方針に反する) |
| B. 範囲分割(頭文字/ID範囲でファイル分割) | 例: 名前の頭文字ごとに分割し、必要な分だけ取得 | 分割単位次第(数百KB程度) | 中 | **不採用**(分割してもなお「クライアントへの索引配信」という性質は変わらず、日本語名・英語名の両対応での分割キー設計が複雑になる割に、次点のCと比べて明確な利点がない) |
| C. サーバー内静的アセット+APIルート経由検索(**採用**) | 索引ファイルをサーバー(Next.jsのビルド成果物/実行時ファイルシステム)にのみ保持し、クライアントへは検索結果(最大件数を絞った一部)のみをAPIレスポンスとして返す | 0(検索結果のみ。PoC実測: 100件検索結果=30 KB) | 中 | **採用** |
| D. クライアント部分読込(遅延・スクロール連動で分割配信) | スクロールに応じて索引の断片を追加取得 | 初回は小さいが累積で最終的に近い量になりうる | 高 | **不採用**(実装コストの割に、Cで要件を満たせるため過剰) |
| E. Supabase統合検索(索引もPostgresへ) | 索引自体もreference_data.world_player_cards等と同じPostgresで検索 | 0 | 低〜中(既存のPostgres検索と統合できる) | **将来検討**(現時点ではworld_player_cardsとの重複が大きく、`player_index_entries`固有の追加情報が限定的なため、今回はCを優先。世界カード方針が安定した後に、索引の一部または全部をPostgresへ統合する余地は残す) |
| F. バージョン管理付き圧縮ファイル | 索引ファイルにdataset_versionを付与しgzip配信 | Cと同様(サーバー内配信ならクライアント量は変わらない) | 低 | **Cの一部として採用**(独立した方式ではなく、Cの実装に versioning + gzip を組み込む) |

### 採用方式の要件

1. **クライアントへ索引全体を配信しない**。既存の`/api/world/players`系APIルートと同様、検索キーワード・ページ番号を受け取り、サーバー内メモリに読み込んだ索引から絞り込んだ結果のみを返す。
2. **最小検索文字数のゲーティング**: 検索語が2文字未満の場合は全件相当のスキャンを行わず、空リスト+ガイダンスメッセージを返す(既存のUXパターンと同様、無意味な巨大スキャンを防ぐ)。
3. **結果件数の上限**: 1リクエストあたり最大100件(PoC実測の「100件検索結果=30 KB」を基準値とする)。
4. **ページング**: `offset`/`limit`のキーセットページングではなく単純offsetページングで十分(索引はサーバー内メモリのため、範囲外アクセスのコストが低い)。
5. **Unicode**: 日本語名・英語名のいずれも大小無視・部分一致検索を行う(既存の`world_player_cards`名前検索と同じ正規化方針を踏襲)。
6. **バージョニング・キャッシュ無効化**: 索引ファイルに`dataset_version`を埋め込み、サーバー起動時またはリクエスト時に読み込んだ索引のバージョンをログ/レスポンスヘッダで確認できるようにする。更新時は新しい索引ファイルに差し替え、旧バージョンとの整合性チェック(件数の急減等)を行ってから切り替える。
7. **ロールバック**: 索引ファイルは`import_batch_id`ごとに世代管理し、直前の世代のファイルを一定期間保持することで即座に切り戻せるようにする。
8. **Preview/Production分離**: 索引ファイルは環境ごとに別ファイル(またはSupabaseの`reference_data`スキーマのように環境ごとに別プロジェクト)として扱い、Preview環境での検証用データがProductionに混入しないようにする。

## 2. 実装

- 純粋関数ライブラリ: `src/lib/reference-data/search-index.ts`
  - `buildSearchIndex(rows, datasetVersion)`: SQLite由来の行から、検索用の軽量エントリ配列(名前・ID・基本属性のみ)を構築する。
  - `searchIndex(index, query, options)`: 最小検索文字数ゲーティング・大小無視/日本語部分一致・結果件数上限・offsetページングを適用して検索する。
  - `MIN_QUERY_LENGTH = 2`、`MAX_RESULTS = 100`をエクスポートし、APIルート側と挙動を一致させる。
- テスト: `src/lib/reference-data/search-index.test.ts`(最小文字数ゲーティング・上限・ページング・Unicode部分一致・空クエリ・バージョン情報の伝搬を検証)。
- 索引ファイルの実際の生成(SQLite→JSON変換)は、既存の`scripts/migration/reference-data-migration-tool.mjs`と同じ「読み取り専用・外部接続なし・Git未追跡出力」の方針を踏襲した専用スクリプトを別途用意する想定とし、**本タスクでは索引JSONの実ファイル生成・Gitへの追加は行わない**(4章)。

## 3. APIルートへの統合方針(設計のみ、実装は既存API変更を伴うため本タスクでは未実施)

- 既存の`/api/world/players`系ルートに、`buildSearchIndex`/`searchIndex`を用いた索引検索の分岐を追加する余地を確認した(既存コードは変更していない)。
- 統合時は、索引検索結果からworld_card_idを取得し、詳細情報は別途Supabase(`reference_data.world_player_cards`)または現行SQLiteから取得する2段階アクセスとする。

## 4. Gitに関する制約の遵守

- 索引JSON(生・gzip問わず)は、変換ロジックが確定し実運用へ移行する判断が下るまで**Gitへ追加しない**。
- 本タスクで生成した検証用データはすべて`data/`配下(`.gitignore`対象)に出力し、`git status`でGit追跡対象に含まれないことを都度確認する。
