## 1. 検証方法の内訳(3層)

RLSによるユーザー別データ分離の証明は、以下の3層に分けて実施した。「実Supabase手動確認済み」と
「自動テスト/SQL静的監査で確認」を明確に区別し、実施していない項目を実施済みと記載しない。

### A. 実Supabase手動確認済み(ユーザー自身がSupabaseダッシュボード・実アプリ画面で操作し確認)

ユーザーA・ユーザーB(いずれもユーザー自身が管理する実Supabaseアカウント)・未認証状態を使い、
`/account/rls-test`画面で以下を確認した。

| # | 確認項目 | 結果 |
|---|---|---|
| 1 | 未認証状態では、検証データの一覧・作成フォームが表示されない | 確認済み |
| 2 | ユーザーAが自分の検証データ(Probe A)を作成できる | 確認済み |
| 3 | 作成した検証データが再読み込み後も残る | 確認済み |
| 4 | ユーザーBへアカウントを切り替えると、ユーザーAの検証データ(Probe A)が一覧に表示されない | 確認済み |
| 5 | ユーザーBが自分の検証データ(Probe B)を作成できる | 確認済み |
| 6 | ユーザーBの一覧には自分の検証データ(Probe B)だけが表示される | 確認済み |
| 7 | ユーザーBが自分の検証データ(Probe B)を削除できる | 確認済み |
| 8 | 再びユーザーAへ切り替えると、ユーザーAの検証データ(Probe A)だけが表示され、ユーザーBの検証データは表示されない | 確認済み |
| 9 | ユーザーAが自分の検証データを更新できる | 確認済み |
| 10 | ユーザーAが自分の検証データを削除できる | 確認済み |
| 11 | 削除後、再読み込みしても削除済みの状態が維持される | 確認済み |
| 12 | 検証終了後、両ユーザーが作成した検証データはすべて削除済み | 確認済み |

**重要な注記**: 「他人のレコードIDを直接指定したSELECT/UPDATE/DELETE」「user_id差し替え」の
実Supabase上での手動確認(ブラウザー開発者ツール経由の直接操作)は、**今回は実施していない**。
これは意図的な省略であり、下記Bの自動テスト・静的監査で同等の保証を別の方法(テストダブル・
構造検証)により確認している。

### B. 自動テストおよびSQL静的監査で確認(実Supabaseへは接続していない)

| # | 確認項目 | 確認方法 |
|---|---|---|
| 1 | 他人のレコードID・存在しないIDへの直接UPDATE/DELETEが0件になり、成功として誤表示されない | Unit Test(`rls-probe.test.ts`)+ ブラックボックス(テストダブル経由のIDOR再現) |
| 2 | user_id差し替え(INSERT時に他人のuser_idを指定・UPDATE時に所有者を変更)が拒否される設計になっている | SQL構造監査(`rls-probe-sql-audit.test.ts`、実ファイルに対しissues 0件を確認済み)。RLSの`WITH CHECK`句とトリガーの両方で拒否する設計をSQL自体から検証 |
| 3 | 未認証でのCRUD操作(アプリのデータアクセス層)が安全に拒否・一般化される | Unit Test + ブラックボックス(未認証状態での画面表示・フォーム非表示を確認) |
| 4 | 0件更新・0件削除を成功として誤表示しない | Unit Test(`rls-probe.test.ts`の専用テスト)+ ブラックボックス(テストダブルでの0件応答シナリオ) |
| 5 | RLSポリシー自体の構造(4種類すべての存在、`auth.uid()`条件、`USING`/`WITH CHECK`、anon/publicへの許可が無いこと、危険な`true`ポリシーが無いこと等) | SQL構造監査(22件の合成SQLケース + 実ファイルへの適用) |
| 6 | 異常入力(空文字・空白のみ・長さ超過・HTML風・script風・SQL風・Unicode・絵文字・バックスラッシュ・引用符・javascript:/data:風の値)がコードとして実行されず、安全に扱われる | Unit Test + ブラックボックス(19種の敵対的入力プローブ) |

### C. 未実施(範囲外・今回の完了条件には含めない)

- ユーザーAのレコードIDを実際にコピーし、ブラウザー開発者ツールから直接SELECT/UPDATE/DELETEを
  試みる実Supabase上での手動操作は、ユーザーの判断で今回はスキップされた。
- 上記Bの自動的な保証で代替しているが、**「実際のPostgreSQL上でのRLS拒否」を人間の目で
  直接確認した，という意味では完全な実施ではない**ことを正直に記録する。

## 2. 総合評価

上記A(実手動確認12項目)とB(自動テスト・静的監査6項目)を組み合わせることで、
「認証済みユーザーごとのデータ分離が安全に成立する」という今回のPoCの目的は、
**実用上十分な確度で確認できた**と判断する。ただし、Cで記載した「他人IDへの直接操作の
実Supabase上での手動確認」は範囲外として明示的に保留した。

## 3. 検証データの後片付け

検証終了後、ユーザーA・ユーザーBが作成した検証データ(Probe A / Probe B / Updated probe)は
すべてユーザー自身の操作により削除済み(ユーザー報告に基づく)。テストユーザーB自体のアカウントは
削除していない(ユーザーの明示的な指示があるまで削除しない方針)。

## 4. 影響範囲

- My Team・お気に入り・保存ビルド・保存スカッド・スカッドテンプレート等の既存localStorageデータは、
  今回のRLS検証において一切Supabaseへ送信していない。
- `rls_probe_records`は検証専用テーブルであり、本番ユーザーデータテーブルは作成していない。
- Secret key・service_role・DBパスワード・Admin APIは、SQL実行時(ユーザー自身によるSQL Editor操作)を
  含め、一切使用していない。
