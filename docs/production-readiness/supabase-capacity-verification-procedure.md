# Supabase Free枠 容量確認手順(2026-09-14)

**本書は上杉さん自身がSupabaseダッシュボードで実施する確認手順である。Claude CodeはSupabaseの契約・プラン画面へアクセスできないため、実際の数値確認は代行できない。** 本書の目的は「何を」「どこで」「何と比較して」確認すべきかを明確にすることであり、数値そのものを断定しない。

対象プロジェクト: 既存の開発用プロジェクト `efootball-team-ai-dev`(ローカル開発・Vercel Preview検証専用。今回は`reference_data`スキーマをまだ追加していない)。

### 保守的見積りとの比較

| | 見積り(2章、Stage 2〜3) | 実測 |
|---|---|---|
| reference_data追加分 | 約55 MB | **約23 MB** |

- 見積りとの乖離は「実測が見積りを上回る」方向ではなく「下回る」方向であり、4章の停止条件(見積りの2倍を超える乖離)には抵触しない。

## 1. 確認する項目と手順

### 1-1. 現在のデータベース使用量

1. Supabaseダッシュボードで対象プロジェクトを開く。
2. 左メニューの **Project Settings → Database**、または **Reports → Database** を開く(バージョンによりメニュー名・位置が異なる場合がある。見つからない場合はスクリーンショットを共有してください)。
3. 「Database size」または「Disk usage」に表示されている現在の使用量(MB)を確認する。
4. これが**参照データ移行前のベースライン**になる(既存の`my_team_snapshots`・`rls_probe_records`・`auth.users`のみを含む値)。

### 1-2. Free枠の上限

1. **Project Settings → Billing**(またはOrganization設定の Billing)を開く。
2. 現在のプラン(Free/Pro等)と、そのプランのDB容量上限(一般に500MB、ただし契約内容によって変わる可能性があるため画面表示を正とする)を確認する。
3. Egress(転送量)・API呼び出し数の上限表示があれば併せて確認する。

### 1-3. 参照データ追加後の想定増分(概算の入り口。詳細は2章)

`player_index_entries`相当の検索索引(47,477件、生4.65 MiB/gzip 1.08 MiB)は**Postgresへは格納しない設計**(サーバー内静的アセットのため、DB容量確認には計上不要)。Postgresへ投入するのは`world_player_cards`・`managers`・`player_card_analysis`・`import_batches`の4テーブルのみ。詳細な3段階見積りは2章を参照。

### 1-4. 既存ユーザーデータとの合算

- 参照データは既存の`public`スキーマとは別の`reference_data`スキーマに置く設計(`create-reference-data-schema.sql`)だが、**Supabaseの容量制限はプロジェクト単位(スキーマ横断)で適用される**ため、既存の`my_team_snapshots`等のユーザーデータと合算した総量で判断する必要がある。
- 既存ユーザー(A・B)のデータ量が今後どの程度増える見込みかも考慮する(本書では見積もらない。運用実績から判断する事項)。

### 1-5. Free-project の自動停止条件

1. **Project Settings → General** または **Infrastructure** で、無操作時の自動停止(一時停止)条件の記載を確認する(`cost-estimate.md`に既存の記載がある「7日間無操作で一時停止」という情報が、現在の契約内容でも有効かを画面で再確認する)。
2. 参照データ追加後、定期アクセス(検索・詳細表示)が発生することで、この自動停止条件に影響するかを確認する(通常はアクセスがあれば停止しないと想定されるが、契約内容次第のため断定しない)。

### 1-6. バックアップ

1. **Database → Backups** を開き、現在のプランで利用可能なバックアップ方式(自動日次バックアップの有無、Point-in-Time Recoveryの有無)を確認する。
2. Free枠では自動バックアップが提供されない場合が多い(`decision-record.md`既存の指摘)。その場合、参照データの実データインポート前に、ロールバックSQL(`rollback-reference-data-schema.sql`)に加えて、インポート直前のスキーマ状態のダンプを手動取得しておくことを推奨する。

### 1-7. Active Project数の上限

1. Organization全体の**Active Projects**数と、現在のプランでの上限を確認する(Free枠は通常プロジェクト数に制限があるため)。
2. 将来Production用に新規プロジェクトを作成する計画(`preview-production-environment-design.md`)がこの上限に抵触しないかを確認する。

## 2. 3段階の保守的な容量見積り

前提数値(実測、`reference-data-migration-poc-results.md`および`scripts/migration/reference-data-migration-tool.mjs`のdry-run実測):

| 対象 | 件数 | JSON表現サイズ(実測、Postgres投入予定分のみ) |
|---|---|---|
| `world_player_cards` | 13,009件 | 23.93 MiB(dry-run実測: 25,091,706バイト) |
| `managers` | 66件 | 0.06 MiB(58,594バイト) |
| `player_card_analysis` | 19件 | 0.03 MiB(28,852バイト) |
| **小計(データ本体のみ)** | - | **約24.02 MiB ≒ 25.2 MB** |

このJSON表現サイズはPostgresの実ディスク使用量そのものではない(行ヘッダ・アライメント・TOAST圧縮・インデックスは別途発生する)ため、以下は**保守的な安全側の概算**として倍率を掛けて見積もる。実際の値は、Stage 1実行後に必ずダッシュボードで再確認すること(1-1節の手順)。

### Stage 1: 初回投入直後(インデックス作成前、データ本体のみ)

- 概算: 25.2 MB × 行オーバーヘッド係数1.3(保守的) ≈ **35 MB**
- 累計(既存26 MB + 35 MB) ≈ **61 MB**(上限500 MBに対し約12.2%、残り約439 MB)

### Stage 2: インデックス作成後

- 対象インデックス: `world_player_cards`にB-tree5本+GIN全文検索1本、`managers`にGIN全文検索1本+B-tree1本(`create-reference-data-schema.sql`参照)。
- 概算: インデックス合計をStage 1データ量の50%(保守的な経験則)と見積もる → 35 MB × 1.5 ≈ **55 MB**
- 累計(既存26 MB + 55 MB) ≈ **81 MB**(上限500 MBに対し約16.2%、残り約419 MB)

### Stage 3: 旧データ世代保持時

- **採用設計**(`reference-data-supabase-update-flow.md`)は、更新のたびに`UPSERT`で現行版のみを保持し、ロールバック用の旧データはPostgres内に複製せずローカルの`*.manifest.json`/変換済みJSON(Git未追跡)で保持する。DB内で増えるのは`import_batches`のメタ行(1行あたり数百バイト)のみ。
- 概算: 月次更新を1年間(12回)実施しても`import_batches`の増分は数KB程度 → **実質無視できる**(Stage 2の81 MBからほぼ変化しない)。
- 参考(不採用の代替設計): 仮にPostgres内で過去N世代をテーブルごと複製保持する設計を採用した場合、単純計算でStage 2見積り×世代数になる(例: 3世代なら 55 MB×3=165 MB相当が追加され、累計は既存26 MB+165 MB≈191 MB)。この設計は採用しないため参考値に留める。

### 3段階のまとめ

| 段階 | reference_data見積り | 累計(既存26 MB込み) | 上限500 MBに対する使用率 | 残容量 |
|---|---|---|---|---|
| Stage 1(データ本体のみ) | 約35 MB | 約61 MB | 約12.2% | 約439 MB |
| Stage 2(インデックス作成後) | 約55 MB | 約81 MB | 約16.2% | 約419 MB |
| Stage 3(旧世代保持、採用設計) | 約55 MB(変化なし) | 約81 MB | 約16.2% | 約419 MB |

### 500 MB上限に対する安全余裕(まとめ)

- 保守的な見積り(Stage 2〜3)でも累計約81 MB、上限500 MBに対し**約84%の余裕(約419 MB)**が残る計算になる。
- ただしこれはJSON表現サイズを起点にした概算であり、実測ではない。**Stage 1実行後(Preview環境での初回投入後)に、必ず1-1節の手順でダッシュボードの実際のDatabase Sizeを確認し、この見積りとの乖離を確認すること**(4章の停止条件も参照)。

## 3. 有償プランへの移行が必要になりうる条件(判断はユーザー自身が行う)

以下のいずれかに該当する場合、有償プラン(Pro等)への移行を検討する必要がある。**本書はこれを判断する材料を提示するのみで、契約変更の実行や推奨は行わない。**

- 2章で算出した見積り、または実測の累計使用量が、1-2で確認した上限に対して余裕がない(目安として上限の80%を超える。4章の停止条件と同じ閾値)。
- バックアップ(1-6)が実運用上必須と判断される。
- Active Project数(1-7)の上限に達し、Production用の新規プロジェクトを作成できない。

## 4. 容量超過時の投入停止条件

以下のいずれかに該当する場合、それ以降の投入(次の段階・次のバッチ)を**停止**し、上杉さんの判断を仰ぐ。自動では継続しない。

| 条件 | 閾値の考え方 |
|---|---|
| 累計Database Sizeの絶対閾値 | ダッシュボードの実測値が**400 MB(上限500 MBの80%)**を超えた時点で、以降の投入・世代追加を停止する |
| 見積りとの著しい乖離 | ある段階を実行した直後の実測増分が、本書2章の見積りの**2倍を超えた**場合、原因(想定外のTOAST膨張・インデックス肥大化等)を調査するまで次の段階へ進まない |
| 単一バッチでの急増 | 1回の投入(1 import_batch)で**50 MBを超える増分**が生じた場合、異常データ(無制限なJSONB膨張・重複行の大量発生等)を疑い、投入を停止して原因調査する |
| Egressの急増 | ダッシュボードのEgressが、現在のベースライン(0.001 GB)から通常の検証操作では説明できない規模まで急増した場合、意図しない全件ダウンロード等の兆候として調査する |
| Active Project数の上限 | Production用の新規プロジェクトを作成する前に、Active Project数が現在のプランの上限に達していないかを確認し、達していれば作成前に停止する(1-7節) |
| 各段階後の実測確認 | 見積りだけで次の段階へ進まず、各段階の実行後に必ずダッシュボードの実測値を確認してから次へ進む |
