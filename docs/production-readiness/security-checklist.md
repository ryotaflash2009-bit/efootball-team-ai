# セキュリティチェックリスト(将来実装時の必須事項)

調査日: 2026-09-11。本書はチェックリストであり、今回は実装しない。将来の認証・DB実装フェーズで、この一覧を満たすことを完了条件とすることを推奨する。

## 1. 秘密情報の取り扱い

- [ ] 秘密情報(APIキー・DB接続文字列・Service Role Key等)をGitへコミットしない(`.gitignore`に`.env*`を含める。**現状Gitリポジトリ自体が存在しないため、初期化と同時に`.gitignore`を用意する**)。
- [ ] クライアント側(ブラウザーで実行されるコード)へ**サービスロールキー(Service Role Key)を絶対に出さない**。RLSをバイパスする権限を持つキーはサーバー側環境変数としてのみ扱う。
- [ ] 環境変数を「クライアントに公開してよいもの(`NEXT_PUBLIC_`接頭辞)」と「サーバー側のみ(接頭辞なし)」に明確に区分する。
- [ ] 開発・ステージング・本番で秘密情報(APIキー・DB接続情報)を分離する(同じ鍵を使い回さない)。

## 2. 認可・アクセス制御

- [ ] RLS(Row Level Security)、またはRLSが使えない構成の場合はサーバー側での認可チェックを、**全てのユーザーデータテーブルに対して**適用する(`data-model-and-isolation.md`)。
- [ ] IDOR(Insecure Direct Object Reference)対策: クライアントから渡されたIDだけで他人のデータへアクセスできないことを確認する。
- [ ] 管理者権限とユーザー権限を明確に分離する(通常のAPIルートはユーザー権限のみで動作させる)。

## 3. Webアプリケーション一般の脆弱性対策

- [ ] CSRF対策(Next.jsのServer Actions/APIルートでのトークン検証、またはSameSite Cookie設定)
- [ ] XSS対策(既存のReactの自動エスケープに加え、危険なHTML挿入(`dangerouslySetInnerHTML`)を新規に導入しない。既存の診断カード等のサニタイズ知見を再利用する)
- [ ] セッション固定(session fixation)対策(ログイン成功時にセッションIDを再発行する、認証サービス標準機能に依存する場合はその実装を確認する)
- [ ] ブルートフォース対策(ログイン試行制限。認証サービス標準機能を優先利用)
- [ ] レート制限(API全般。既存の`/api/build-intent/extract`のプロセス内スロットリングパターンを参考に、認証・移行関連のAPIにも同様の考え方を適用する)
- [ ] メールアドレス列挙対策(「そのメールは登録されていません」のような、登録有無が分かるエラーメッセージを避ける。認証サービス標準の設計に従う)
- [ ] パスワードリセット悪用対策(リセットリンクの有効期限・使い切り、認証サービス標準機能に依存)
- [ ] 安全なCookie設定(`Secure`, `HttpOnly`, `SameSite`属性。認証サービスのSDKが標準対応しているか確認する)
- [ ] HTTPS強制(Vercel等のホスティングは標準でHTTPSを提供するため、追加設定は少ない見込み)
- [ ] CSP(Content Security Policy)ヘッダーの設定(Next.jsの`headers()`設定で追加。既存の外部リソース利用状況(画像プロキシのみ)を踏まえて設計する)
- [ ] その他セキュリティヘッダー(`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`等)
- [ ] 依存関係の脆弱性監査(`npm audit`、GitHub Dependabot。`ci-cd-and-auto-update.md`参照)

## 4. データ保護

- [ ] 管理者権限の分離(前述と重複するが重要事項として再掲)
- [ ] 監査ログ(誰が・いつ・何を変更したかを追跡できる仕組み。`data_migrations`・`user_exports`・`account_deletion_requests`テーブルが一部を担う)
- [ ] アカウント削除機能の実装(データモデルで設計済み、`data-model-and-isolation.md`)
- [ ] データ保持期間の明文化(削除猶予期間・バックアップ保持期間をプライバシーポリシーへ反映する際は、実装内容と一致させる)
- [ ] バックアップの暗号化(契約するDBサービスの標準仕様を確認する。自前で追加の暗号化を行うかは規模に応じて判断)
- [ ] ログから個人情報を除外する(`monitoring-and-logging.md`第2章)

## 5. 実装前チェック(このチェックリストの使い方)

将来、認証・クラウドDBの実装に着手する際は、実装完了の判定基準として本チェックリストの全項目を満たすことを条件とする。現時点(本タスク)ではいずれも**未実装**であり、それ自体は正常(今回のスコープ外)。
