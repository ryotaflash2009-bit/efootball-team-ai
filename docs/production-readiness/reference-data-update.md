# 選手・カード参照データの半自動更新設計

調査日: 2026-09-11。本書は設計のみ。実際のデータ取得・本番反映は今回行わない。

## 1. 大原則: サイト本体のデプロイと参照データ更新を分離する

現状、選手・カードデータ(SQLite `data/efootball.db`)は`scripts/fetch-player-index.mjs`等の一度限りの手動同期スクリプトで作られている。サイト本体(コード)のリリースサイクルと、参照データの更新サイクルは**頻度も承認基準も異なる**ため、明確に別系統として設計する。

## 2. 推奨フロー(タスク要求の14ステップをそのまま採用)

```
1.  ソースから取得          (efootball-world.com / 過去のeFHUB等、既存の取得スクリプトの発展形)
2.  ステージング領域へ保存   (本番SQLiteとは別ファイル。例: efootball.staging.db)
3.  スキーマ検証            (既存のZodスキーマ・SQLiteスキーマ検証を再利用)
4.  件数比較               (前回版との総件数差分を算出)
5.  重複確認               (worldCardId等の一意性チェック)
6.  削除件数確認            (前回版に存在し今回消えたレコード数)
7.  変更差分作成            (追加/更新/削除の一覧をレポート化)
8.  異常値検出             (負の値・極端な外れ値等)
9.  能力値範囲確認          (26能力値が既知の範囲(0-99等、既存の計算エンジンが前提とする範囲)内か)
10. 既存計算テスト          (calculateBuild等の既存Unit Testを、新データの代表サンプルに対して実行)
11. ブラックボックス        (Production Build + 新データで、既存の主要な回帴シナリオを再実行)
12. 人による承認           ★自動化しない
13. 本番データ公開          (承認後、本番SQLiteファイルを差し替え)
14. 問題時に前のデータ版へ戻す (バージョン管理された旧ファイルへ即時切り戻し)
```

## 3. 初期版は完全自動反映ではなく半自動更新を推奨する理由

- 選手・カードデータの提供元(`efootball-world.com`等)は、`docs/efootball-world-data-investigation.md`・`docs/data-verification.md`の既存調査で確認した通り、**再配布を明示的に許諾する文書が確認できていない第三者サイト**である。
- 「権利関係が未確認の情報源から、自動で本番へ公開する構成を作らない」というタスクの明示的な要求に従い、**ステップ12(人による承認)を必ず挟む**。
- データの中身が変わる(選手能力値の改定、新カード追加等)ことは、利用者の育成計算結果に直接影響するため、機械的な自動反映のリスクが特に大きい領域である。

## 4. 安全停止条件(タスク要求+既存データからの具体化)

| 条件 | 具体的な閾値の考え方 |
|---|---|
| カード件数の大幅減少 | 前回比で一定割合(例: 5%超)減少した場合は自動停止し、人へ通知(閾値は実装時に既存件数13,009件を基準に調整) |
| 未知フィールドの大量発生 | 既存Zodスキーマの`.passthrough()`で許容している未知キー(`data-verification.md`で確認した`c`キーの前例)が、一定件数を超えて新規出現した場合は要確認として停止 |
| 能力値範囲外 | 26能力値のいずれかが既存の許容範囲を外れるレコードが1件でもあれば停止 |
| 重複急増 | 一意キー(`worldCardId`)の重複が閾値を超えたら停止 |
| 画像URLの大量変更 | 許可ホスト(`d1zxa6glxh8sq9.cloudfront.net`等)以外のドメインへ画像URLが変化した場合、または変更件数が急増した場合は停止(既存の`isAllowedWorldImageUrl`等の許可ホストチェックをステージング検証段階でも適用する) |
| 計算テスト失敗 | 既存Unit Test(`calculateBuild`関連)が新データのサンプルに対して1件でも失敗したら停止 |
| 参照元の利用条件変更 | 定期的に取得元の`robots.txt`・利用規約ページを確認し、取得を制限する記述が追加されていないか確認するプロセスを設ける(自動検知は困難なため、更新作業のたびに人が目視確認する運用を推奨) |
| 取得失敗 | HTTPエラー・タイムアウト・空レスポンス等は即座に停止し、前回データをそのまま維持する(既存の`fetch-player-index.mjs`が既に採用している「取得失敗時はファイルを書かず終了コード1」という安全設計を踏襲) |
| 差分が想定より大きい | 追加/更新/削除件数の合計が、直近の平均的な差分から大きく外れる場合は要確認として停止 |

## 5. バージョン管理・ロールバック

- 本番SQLiteファイルは、日付やハッシュを含むファイル名で**版管理**する(例: `efootball.2026-09-11.db`)。現在の本番ファイルへのシンボリックリンク/参照ポインタを切り替える方式にすることで、即座に前版へ戻せる。
- 少なくとも直近数世代分は保持し、問題発覚時にすぐ戻せるようにする(具体的な保持世代数は運用コスト次第で決定)。

## 6. 本番デプロイとの関係

- 参照データの更新は、**サイト本体のコードデプロイとは独立したパイプライン**として設計する(`ci-cd-and-auto-update.md`の自動デプロイとは別トリガー)。
- Vercel等のホスティングへ読み取り専用SQLiteを同梱する構成(`hosting-options.md`参照)を採用する場合、「参照データだけを更新する」ことが「サイト全体の再デプロイ」を意味してしまう可能性がある点に注意が必要(この場合、参照データ更新の頻度がサイトの再デプロイ頻度と実質的に結合する)。この技術的制約を踏まえ、**参照データをホスティングとは別のオブジェクトストレージ等から実行時に読み込む方式への切り替えも将来検討する価値がある**(今回は設計課題として記録するに留め、結論は出さない)。
