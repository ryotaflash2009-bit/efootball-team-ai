# localStorageからクラウドへの移行設計

調査日: 2026-09-11。本書は設計のみであり、今回は実装しない。

## 1. 移行対象データ

`architecture-audit.md`の分類Aに基づき、移行対象は **Favorites・My Team・保存ビルド(`buildIntent`込み)・保存スカッド・スカッドテンプレート** の5種類。分類B・C(表示言語・サイドバー状態・スカッド編集設定・スカッド比較の直前状態)は移行しない。

## 2. 設計原則(タスク要求への対応)

| 原則 | 設計 |
|---|---|
| ログインしただけで勝手にアップロードしない | ログイン成功後、自動アップロードは**行わない**。「クラウドへ移行しますか?」という明示的な確認画面を必ず挟む。 |
| 移行前にJSONバックアップを案内 | 移行確認画面の最初に、既存の「データ管理」ページのJSONバックアップ機能への導線を必須表示し、「先にバックアップを取ることを強く推奨」する文言を出す。 |
| 移行対象件数を表示 | 「Favorites: n件、My Team: n件、保存ビルド: n件、保存スカッド: n件、スカッドテンプレート: n件」を移行確認画面に事前表示する。 |
| ユーザーの明示操作で開始 | 「クラウドへ移行する」ボタンを明示的にクリックした場合のみ開始する(自動実行トリガーは一切設けない)。 |
| 移行前に内容を検証 | 既存の`Zod`スキーマ(各`*-storage.ts`が既に持つ検証ロジック)を再利用し、壊れたデータは移行対象から除外して警告表示する(既存の「壊れたデータは黙って捨てる」方針を踏襲)。 |
| 一度に全データを破壊しない | 5種類のデータは**種類ごとに独立したステップ**として移行する(Favorites→My Team→保存ビルド→保存スカッド→スカッドテンプレートの順)。1種類が失敗しても他の種類の移行結果には影響しない。 |
| 移行成功前にlocalStorageを削除しない | 移行処理自体はlocalStorageを**一切変更しない**(読み取り専用)。削除は完全に別の、ユーザーが後から明示的に行う操作(下記「7. 移行後のlocalStorage扱い」)。 |
| 部分成功を安全に扱う | 種類ごとの成功/失敗/スキップ件数を個別に記録し、「Favorites: 12件成功、My Team: 8件成功・1件失敗(理由表示)」のように結果画面へ提示する。失敗した項目だけを再試行できるようにする。 |
| 再試行可能 | 移行処理は**冪等**に設計する(後述「4. 重複検出」)。何度実行しても安全。 |
| 重複を検出 | クラウド側に既に同じ`worldCardId`(Favorites/My Team)や同じ内容のハッシュ(保存ビルド等)が存在する場合は「重複」として検出し、上書きしない。 |
| 別ユーザーへ誤移行しない | 移行処理は必ず**認証済みセッションから取得した`user_id`**のみを使い、クライアントから`user_id`を渡す設計は禁止する(`data-model-and-isolation.md`のIDOR対策と同一原則)。 |
| 同じデータを二重作成しない | 上記「重複を検出」と同じ機構で担保する。 |
| 移行後も一定期間localStorageを保持 | 移行成功後もlocalStorageは**自動削除しない**。既定では無期限に残す(明示的な削除操作を待つ)。 |
| ユーザーが確認してからローカル版を削除 | 移行結果画面に「ローカルのデータを削除しますか?(クラウドへの移行が完了しています)」という**別ステップの確認**を用意し、ここでも二段階確認(既存の`/data-management`の「全データ削除」機能と同じUXパターン)を踏襲する。 |
| JSONからの復元も維持 | 既存の保存ビルドJSONインポート機能は**そのまま維持**する。クラウド移行後も「JSONから保存ビルドを追加インポートする」経路を廃止しない(オフライン機での作業結果を後から取り込みたいケースに対応)。 |

## 3. 移行フロー(概念)

```
1. ログイン成功
2. (自動アップロードなし。通常の画面へ遷移)
3. ユーザーが「データ管理」ページ等から「クラウドへ移行」を明示的に開始
4. バックアップ案内 + 移行対象件数の表示
5. 「移行を開始する」ボタン(明示操作)
6. 種類ごとに順番に処理:
   a. localStorageから読み取り
   b. Zod検証(既存スキーマを再利用)
   c. 重複チェック(クラウド側に問い合わせ)
   d. 重複時の処理方針(下記4章)を適用
   e. 挿入/更新
   f. 結果を記録(成功/失敗/スキップ件数)
7. 全種類の結果をまとめて表示(部分成功も正直に表示)
8. 失敗分があれば「この項目だけ再試行」ボタンを提示
9. (別ステップ、後日でも可)「ローカルデータを削除しますか?」の確認 → 既存の削除フロー(二段階確認)を再利用
```

## 4. 重複時の選択肢

タスクで要求された4方式(クラウドを維持/ローカルで上書き/両方保持/項目ごとに選択)を評価した結果、**初期版では単純な安全側の方式を推奨する**:

### 推奨(初期版): 「クラウドに存在しないものだけを追加する」単純方式

- Favorites・My Team: `worldCardId`が既にクラウド側に存在すれば**スキップ**(上書きしない)。存在しなければ追加。
- 保存ビルド・保存スカッド・スカッドテンプレート: 名称+内容のハッシュが完全一致すれば**スキップ**。一致しなければ**新規レコードとして追加**(同名でも別レコードになり得るが、データを失うことは絶対にない、という安全側の判断)。

**理由**: 「両方保持」「項目ごとに選択」は最も安全にデータを失わないが、UIが複雑になり初期のベータ利用者には分かりにくい。「クラウドを維持」「ローカルで上書き」はどちらも**データを失う可能性がある**(タスクの「一度に全データを破壊しない」原則に反するリスクがある)。上記の「存在しないものだけ追加」方式は、既存データを一切破壊せず、かつUIも単純(確認ダイアログ不要)にできる。

### 将来の拡張(正式公開後)

利用者からのフィードバック次第で、「項目ごとに選択」できるUIへ拡張する余地を残す(データモデル側に移行元(local/cloud)・移行日時を記録しておけば、後からマージUIを追加しやすい)。

## 5. 移行失敗時の安全性

- ネットワークエラー・認証切れ等で移行が中断した場合、**それまでに成功した種類のデータはクラウド側に残る**(ロールバックしない。中途半端でも「進んだ分は進んだまま」として扱う。これは各データ種別が独立しているため安全)。
- 失敗した種類は「未移行」のまま何度でも再試行できる。
- 移行処理は**サーバー側のトランザクション内で1種類ずつ完結**させ、1レコードの挿入途中でエラーが起きても、その種類の他のレコードには影響しない設計とする(1レコード=1トランザクション、または種類ごとにバッチ+部分失敗許容)。

## 6. 移行対象件数がゼロの場合

Favorites等が空の場合はそのまま「0件」と表示し、エラー扱いにしない(既存データが無いこと自体は正常な状態)。

## 7. 移行後のlocalStorageの扱い

- 移行完了後もlocalStorageは自動的には削除しない。
- ユーザーが「データ管理」ページで明示的に「ローカルのデータを削除する」を選んだ場合のみ、既存の`deleteAllManagedLocalData()`(前フェーズで実装済み)を呼び出す。この関数は**既に安全に実装済み**(管理対象キーのみ削除、SQLite不変、二段階確認)であり、クラウド移行機能を実装する際もこの既存関数をそのまま再利用できる設計とする。

## 8. 未確定事項

- 「重複検出」の具体的なハッシュ計算方式(保存ビルドの内容をどう正規化してハッシュ化するか)は、実装時に個別設計が必要。
- 大量データ(例: 保存ビルドが数百件)の移行時のタイムアウト・進捗表示の詳細は未設計(実装フェーズで検討)。
