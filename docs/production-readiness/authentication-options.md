# 認証: 要件整理とサービス候補比較

調査日: 2026-09-11。料金・仕様は各社公式サイトおよび複数の第三者解説記事(いずれも2026年時点の内容として検索で取得)を根拠とする。**価格は変動するため、実際に契約する直前に必ず公式サイトで再確認すること。**

## 1. 将来必要な認証機能の整理

| 機能 | ベータ版(招待制)で必須 | 正式公開後でよい |
|---|---|---|
| 新規登録(メール+パスワード、またはメールリンク) | ✅ 必須 | - |
| ログイン | ✅ 必須 | - |
| ログアウト | ✅ 必須 | - |
| メールアドレス確認 | ✅ 必須(なりすまし登録・誤入力対策として初期から) | - |
| パスワード再設定 | ✅ 必須 | - |
| セッション管理(有効期限・トークン更新) | ✅ 必須 | - |
| 別端末でのログイン(同一アカウントで複数端末から利用) | ✅ 必須(そもそも同期の主目的) | - |
| アカウント削除 | ✅ 必須(データ管理ページの「全データ削除」と対になる権利) | - |
| 全セッションログアウト(不正利用時に全端末を強制ログアウト) | - | 正式公開後でよい(招待制ベータの人数規模では優先度が低い) |
| ログイン試行制限(ブルートフォース対策) | ✅ 必須(採用する認証サービスが標準搭載しているものを利用) | - |
| 不正アクセス対策(異常なIPからの大量試行等) | 採用サービス標準機能に依存(初期は標準搭載分で可) | 独自の高度な検知は正式公開後 |
| 二要素認証(2FA) | - | 正式公開後でよい(候補サービスはいずれも将来追加可能) |
| OAuth(Google等でのログイン) | - | 初期はメール認証のみで十分。正式公開時に追加を検討 |

## 2. 公開ユーザーIDと非公開内部ユーザーIDの分離

- **非公開内部ユーザーID**: 認証サービスが発行するUUID等。DBの外部キーとして使うが、**他ユーザー向け画面には一切表示しない**。
- **公開ユーザーID**: 将来、ユーザー同士が「フレンド」等で関わる場合に見せてよい短い識別子(例: `u_xxxxxxxx`のような、内部UUIDとは別に生成するランダム文字列、または本人が設定する一意なハンドル名)。**メールアドレス・内部UUIDのいずれも公開ユーザーIDとして流用しない。**
- **表示名**: 本人が設定する任意の文字列(本名を強制しない)。既存の危険文字列サニタイズの知見(診断カード等で既に確立済み)を再利用する。
- メールアドレスは**プロフィール編集画面など本人だけが見る画面以外には一切表示しない**設計を必須要件とする。

## 3. 認証候補の比較

比較対象: **Supabase Auth**、**Firebase Authentication**、**Clerk**、**Auth.js(旧NextAuth.js)+独自DB**。

| 項目 | Supabase Auth | Firebase Authentication | Clerk | Auth.js + 独自DB |
|---|---|---|---|---|
| 無料枠 | 50,000 MAU無料(2026年時点) | メール/ソーシャル/匿名ログインは50,000 MAUまで無料(電話番号認証は無料枠なし) | 2026年2月改定で**50,000 MRU(Monthly Retained Users)**まで無料。MRUはMAUより狭い定義(1度きりのサインアップは含まない) | 完全無料・自己ホスト。ユーザー数無制限(自前DBの容量・性能が上限) |
| 超過時の費用 | 追加$0.00325/MAU | 追加$0.0055/MAU(電話番号は別建て) | Proプランは$20/月〜(段階的) | 追加費用なし(自前インフラのコストのみ) |
| メール認証 | あり | あり | あり | 自分で実装(メール送信サービスが別途必要) |
| パスワード再設定 | あり | あり | あり | 自分で実装 |
| OAuth | 主要プロバイダ対応 | 主要プロバイダ対応 | 主要プロバイダ対応 | プロバイダごとに個別設定(50以上のプロバイダに対応する組み込みアダプタあり) |
| 二要素認証 | あり(Pro以降で拡張) | あり | あり | 自分で実装が必要 |
| Next.js対応 | 公式SDK・App Router対応良好 | 公式SDKあり(App Routerでの取り回しはSupabase/Clerkよりやや手間) | Next.js公式サポートが手厚い(App Router専用ミドルウェア等) | Next.js専用ライブラリ(元々Next.js専用として開発) |
| React Native対応 | 対応(Expo管理ワークフローでも動作) | 対応(`@react-native-firebase`が必要、Expo Goでは一部機能不可・開発ビルドが必要) | 対応(公式にReact Native向けガイドあり) | React Native向けの公式サポートは薄い(Web専用に近い) |
| ユーザーDBとの連携 | **同一Postgres内にauthスキーマがあり、アプリ用テーブルと同じDBで完結** | 別サービス(Firestore/Realtime DB)との連携が必要 | 外部DB(Supabase/Neon等)と別途連携する設計が前提 | 自前DBそのものに認証情報も格納(統合しやすいが自己責任) |
| 行レベルセキュリティ(RLS) | **PostgresネイティブのRLSをそのまま利用可能** | Firestoreのセキュリティルールで同等の制御(構文は別物) | 認証のみ提供。RLSは接続先DB側(Supabase等)に依存 | 自前DBのアプリケーションコードで制御(RLS相当の仕組みは自作) |
| アカウント削除 | API提供 | API提供 | API提供 | 自分で実装 |
| データエクスポート | SQLで自由に取得可能 | Firestoreエクスポート機能 | ユーザー情報のみ(アプリデータは別DB側の責務) | 自前DBから自由に取得可能 |
| 管理画面 | Supabase Studio(無料枠でも利用可) | Firebaseコンソール | Clerkダッシュボード | なし(自作が必要) |
| ベンダーロックイン | 中程度(PostgresなのでDBごとエクスポート可能。Authスキーマは移行作業が必要) | 高い(Firestoreはドキュメント指向でNoSQL、移行コストが大きい) | 中程度(認証のみの責務なので、DB側は自由に選べる) | 低い(標準的なDB+自前実装なので最も移植性が高い) |
| ローカル開発 | Supabase CLIでローカルPostgres+Authを再現可能 | Firebaseエミュレータスイートあり | ローカル向けの簡易モードあり(本番同等のクラウド依存はやや強い) | 完全にローカルで動作(自前DBがあれば良い) |
| バックアップ | Postgresの標準バックアップ機構に準拠(有料プランでPITR) | Google Cloud側のバックアップ機能 | 認証データのみ(Clerk側の責務) | 自前DBのバックアップ運用がそのまま適用される |
| 障害時の影響 | Supabase障害時はログイン・アプリDBの両方が止まる(同一基盤) | Firebase障害時はログインのみ影響(DB側は別選択も可能) | Clerk障害時はログインのみ影響(DB側は独立) | 自前DBとアプリが同一障害ドメイン(自分の運用次第) |
| 設定の難易度 | 中(Postgres・RLSの理解が必要) | 中(NoSQLのデータモデリングに慣れが必要) | **低い(認証だけに特化しており最も簡単)** | 高い(自分でセッション管理・DBスキーマを設計する必要) |
| 高校生の個人開発としての運用負担 | 中(DBと認証が一体なので管理対象は少ないが、Postgres/RLSの学習コストあり) | 中〜高(NoSQLモデリング+Google Cloud特有の概念) | **低い(認証専業なので迷いにくい。ただしDBは別途Supabase等が必要になり、結局2サービス運用になる)** | 高い(実装量が最も多く、セキュリティ不備のリスクも自己責任になりやすい) |

## 4. 所見(この文書内での比較のみ。次章「推奨構成」で最終判断)

- **Supabase Authは「認証とDBが同じPostgres上で完結する」という点が、個人開発者にとって最大の利点**になり得る。RLSも標準機能であり、本タスクの「ユーザー別データ分離」要件と直接噛み合う。
- **Clerkは認証体験の作り込みが最も簡単**だが、DBは別サービス(Supabase等)が必要になるため、結局2サービス運用になる。
- **Firebaseは無料枠が大きい一方、既存のPostgres指向のデータモデル(users, favorites, saved_builds等のリレーショナルな構造)とはFirestoreのドキュメント指向モデルが噛み合いにくい。**
- **Auth.js + 独自DBは、費用ゼロ・柔軟性最大だが、実装量とセキュリティ責任が最も重い**。2026年時点でAuth.js自体は保守モード(新機能追加なし、セキュリティ更新のみ)であることも確認されており、積極採用にはやや不安が残る。
